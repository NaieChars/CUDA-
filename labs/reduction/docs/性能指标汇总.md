# 并行归约：性能指标汇总

2026-10-16。进行三版核函数跑分，分析正文在前，未经平均的原始样本折叠在后。

## 1. 实验边界与结果

- RTX 5060 Laptop GPU，26 SM，L2=32 MiB，驱动 592.00，CUDA 12.8.61，Nsight Compute 2025.2.0；Windows，Release、原配置 native 架构、-lineinfo。
- 固定 n=16,777,216（64 MiB）、block=256。主比较 I=1/4/4；另加 multi_item/shuffle 的 I=1 控制组。232 组正确性检查全部 PASS：三种 block（32/256/1024）、I=1/3/4/64（基础版仅 1）、小尺寸和 chunk 边界。每次计时与采集另有框架校验。输入与容差见 main.cu，不能据此保证任意浮点分布的误差。
- 完整归约：每次进程预热 30 次、CUDA events 计时 300 次后取平均；每配置重复 10 个进程。按轮次循环移动配置顺序，不删除慢样本。时间包括全部归约轮次及 GPU 时间线中的提交间隙，排除分配、H2D/D2H 和 CPU 校验。
- 首轮 NCU：每配置 3 次、kernel replay、cache-control=all。采集 45 项；clock-control=none 为接近普通运行的主诊断，base 为低频对照。另补 9 项 L1/TEX 子管线指标。NCU 的冷缓存、回放及频率控制与普通计时不同，不能直接把两者耗时相减来算尾轮/启动开销。
- 三版均为 3 次 kernel：shared 为 16,777,216→65,536→256→1，其余 I=4 为 16,777,216→16,384→16→1；本例的收益不来自少启动 kernel。

主结果：multi_item / shuffle 相对 shared 的平均时间加速分别为 2.328× / 2.313×。shuffle−multi_item 的轮次配对时间差均值为 1.30 μs，95% t 区间 [-5.17, 7.77] μs：本批重复运行未建立稳定的快慢关系，不能说 shuffle 已获额外加速，也不能证明两者严格等效。该区间依赖近似独立同分布假设，不能覆盖全部温度/调度环境。

输入有效带宽分子仅为 n×4；不是转置的 2n×4，也不是实测 DRAM 总流量。GB/s 为十进制；逐次带宽的均值与“输入字节/平均时间”略有差别。

## 2. 只追踪能解释差异的证据

| 自然频率首轮；3 次均值 | shared I=1 | multi_item I=4 | shuffle I=4 |
| --- | --- | --- | --- |
| 首轮 μs | 462.37 | 200.07 | 199.17 |
| 实际 SM GHz | 2.69 | 2.69 | 2.49 |
| DRAM 吞吐 % | 45.91 | 97.67 | 97.47 |
| 动态 warp 指令（百万） | 64.03 | 24.43 | 13.53 |
| shared load warp 指令 | 1,638,400.00 | 409,600.00 | 16,384.00 |
| shared store warp 指令 | 1,310,720.00 | 327,680.00 | 131,072.00 |
| Occupancy % | 85.85 | 91.69 | 87.81 |
| Eligible warps / scheduler active cycle | 0.84 | 0.85 | 0.44 |
| Issue active %（elapsed） | 49.44 | 43.69 | 26.31 |
| Long scoreboard / issue-active 原始 ratio | 6.86 | 14.57 | 33.22 |

**① shared→multi_item：先证明减少了哪一类工作。** 三版首轮 global load 都是 524,288 个 request、2,097,152 个 sector，即 4 sector/request；每个 request 对应完整 warp 的 32 个连续 float，合并读取已达到该访问形式的理想值。I=4 没有少读原始输入，也没有“再次改善合并访存”。block 数减为 1/4；shared load/store warp 指令由 1,638,400/1,310,720 降为 409,600/327,680，均恰好减为 1/4；总 warp 指令由 64.029M 降为 24.429M（减少 61.8%），每输入指令从 3.816 降为 1.456。证据支持摊薄 block 内通信/控制成本。

进一步拆解：补采的 shared 版 L1/TEX throughput=87.36%，与 l1tex__lsuin_requests=87.36% 一致；shared data-pipe wavefront 利用率只有 43.51%。高的是 LSU 请求入口压力，不是 L1 命中率好，也不足以称为 shared 数据带宽打满。自然频率主采样中 barrier/short-scoreboard 累积 warp-cycle 从 189.47M/289.13M 降到 47.32M/62.56M。它们与结构变化方向一致，但不能分拆成各自贡献多少微秒，更不能简单相加当作 kernel 时间。

**② multi_item→shuffle：通信确实减少，但瓶颈已迁移。** I=4、grid 和读入数据保持相同；shared load/store warp 指令再降为 16,384/131,072（分别减少 96%/60%），总 warp 指令从 24.429M 降为 13.533M（减少 44.6%）。源码每 block 的屏障由 8 次降为 1 次。但自然频率下两者 DRAM 吞吐为 97.67%/97.47%，首轮 200.07/199.17 μs，整段普通计时差异落在波动内。这里已接近当前采样条件的 DRAM 上限，减少内部工作不必继续减少总时间。

这里的 97% 只属于自然频率、冷缓存的 NCU 场景，不能直接贴到普通计时上。普通运行没有同步采集区间内的频率和 DRAM 计数，因此“普通计时为何没有额外收益”的带宽解释与证据一致，但尚不能精确拆分其中的带宽、尾轮和提交间隙份额。

代价也要看：shuffle 的有效线程 FADD 数是 39,862,272，反而高于 multi_item 的 20,955,136。所有 lane 都执行 shuffle 加法，较高 lane 的中间结果没有用作最终和。本版用额外的局部算术换取通信/控制减少；不能用 FLOP 更少或指令更少中的单一指标评价算法。


| 频率对照 | base 首轮 μs | base SM GHz | base DRAM % | none 首轮 μs | none SM GHz |
| --- | --- | --- | --- | --- | --- |
| shared I=1 | 842.46 | 1.410 | 24.42 | 462.37 | 2.694 |
| multi_item I=4 | 266.67 | 1.356 | 76.09 | 200.07 | 2.687 |
| shuffle I=4 | 201.87 | 1.328 | 96.98 | 199.17 | 2.492 |

这项对照解释了“为什么只看默认 profiler 会得出不同的优化收益”：base 下 multi_item→shuffle 为 266.67→201.87 μs，时间减少 24.3%；自然频率下只差约 0.45%。两组 NCU 的内存时钟均约 10.99 GHz，SM 则明显不同，且 none 组各版本的实际 SM 时钟也不同，所以这是运行条件敏感性证据，不是严格同频核心效率测试。所有版本的快慢结论必须附带工作负载和频率条件。

**③ Eligible / stall 不能脱离吞吐读。** 自然频率下 shuffle 的 eligible 从 0.85 降到 0.44、issue 从 43.69% 降到 26.31%，却仍维持相同 DRAM 吞吐。减少要发射的工作后，scheduler 不必更忙才能达到相同目标速度。long-scoreboard/issue-active ratio 从 14.57 升到 33.22；它不是耗时百分比，分母随指令/issue 数改变。即使换成 long_scoreboard.sum / warps_active.sum，也只是累积 warp-cycle 中的状态占比（57.8%→77.9%），不能当作 kernel 有 77.9% 时间可直接消除。当前证据首先指向带宽上限，不支持凭高 long scoreboard 就添加更多 warp。

**④ 有控制组，才不会把额外代价归错因。** I=1 的 multi_item 比 shared 慢：516.65 vs 470.09 μs；低频对照的 warp 指令为 83.034M vs 64.029M，FADD 为 33.489M vs 16.712M，shared 树指令数量相同。额外的局部累加和动态循环不是免费的。两版寄存器由 16 增到 40，但 registers 的驻留上限分别为 16/6 block，线程/warp 上限都是 6 block，理论 occupancy 都可到 100%；不能把这里的慢直接归因于寄存器导致 occupancy 下降。

## 3. 本轮暂时降低优先级的指标，以及证据边界

- **L1/L2 hit rate**：输入 64 MiB，大于 32 MiB L2，首轮每元素只读一次；NCU 还明确清缓存。主采样 L1 命中约 0.25%～0.76%，L2 约 0.78%～2.58%。缓存命中率不是本次优化目标，不能为了抬高它增加重复访问。此结论不推广到可驻留缓存的小数组或真实融合算子。
- **Bank conflict**：读侧计数/读 wavefront 仅约 0.02%～0.12%，写侧约 1.0%～3.4%，不是零，但当前相对主体工作量较小。已知源码访问没有转置式跨 bank 步长；不能把 shuffle 的收益解释为修复了严重 bank conflict。细小非零计数来自哪条指令尚未定位，需要源码/SASS 关联的理想与实际 wavefront、必要时 PC sampling 后再下结论。
- **Occupancy 与 shared 容量**：三版实际 shared 分配均为 2,048 byte/block（launcher 请求 1,024，不能把使用槽位变少等同分配变少）；shared 驻留限制 16 block，不是最紧的 6 block 限制。自然频率 occupancy 为 85.85%/91.69%/87.81%，没有出现低 occupancy 使主比较无法供给带宽的证据，暂不为提高百分比而优化。
- **DRAM 写字节、聚合 cache throughput**：各次 DRAM 写回和部分 read 样本波动较大，写回可能不与该 kernel 的输出 payload 一一对应，且未隔离桌面其他 GPU 活动；保留全部原值，不拿额外字节直接推导 kernel 冗余访存。判断访问模式优先使用本 kernel 稳定的 request/sector。聚合 throughput 是组成子指标的最大值，不等同某种缓存命中率或有效带宽。
- **尚不能回答的因果问题**：某个 barrier 的具体等待位置，需要 SourceCounters/PC sampling 与 SASS 对应；尾轮与提交间隙分别占多少，需要同一环境的逐轮 events 或 Nsight Systems 时间线；小尺寸、其他 B/I 或更复杂输入的结论需要相应扫描。本轮不凭这批数据外推，也不将减少的指令数直接换算成加速比。

## 4. 可迁移的分析顺序

1. 先固定目标时间、输入、配置、校验与重复性；把完整算子时间和被 profile 的局部范围分清。
2. 根据代码提出一个具体预测，并列出不变量：例如读入量不变、block 数减少，或 grid 不变、通信减少。
3. 用 counts 验证预测，并按输入元素/输出元素归一化；不要只看百分比。
4. 联合耗时、资源吞吐、eligible/issue 与依赖状态，判断当前约束；高 stall 单项不是结论。
5. 改一个因素做对照，核对时钟、cache 与 replay；没有稳定差异就报告不确定性。优化后重新诊断，因为瓶颈会迁移。

资料：[NCU Profiling Guide：Replay / Clock / Cache / throughput / scheduler](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)，[NCU CLI 参数](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html)。本机 2025.2 的 ncu --help 与随附 ProfilingGuide 确认 clock-control 默认 base、cache-control 默认 all；新版本在线指南行为可能变化，优先核对安装版本。
