# SGEMM：性能指标汇总

2026-10-19。三版实测完成；正文围绕诊断证据，未经平均的原始数据折叠在后。没有修改三个 GPU 核函数。

## 1. 测量口径与结论

- RTX 5060 Laptop GPU，26 SM、L2 32 MiB、每 SM 最多 1,536 线程和 65,536 个 32 位寄存器；驱动 592.00、CUDA 12.8.61、NCU 2025.2.0。Windows Release、实际 cubin 为 sm_120、启用 -lineinfo；三版均为 FP32 普通乘加。
- 三版 block 均为 16×16；naive/shared 输出 tile 为 16×16，register 为 32×32、每线程四个输出。shared/register 的 BK 均为 16，launcher 动态 shared 请求分别为 0/2/4 KiB。
- 重建后三版共 24 组小尺寸/矩形/尾部全量 CPU-double 数值检查通过；后续每次普通计时及 NCU 另做前后校验。shared/register 在 65×67×33 上分别通过 racecheck 和 synccheck；这只覆盖该样例。输入为框架的确定性混合正负二进制分数，atol=rtol=1e-4，不代表任意浮点分布的精度保证。
- 普通计时：每配置独立运行 10 个进程，每进程预热 30 次、events 区间重复 300 次取平均。配置按轮次循环移位，无慢样本剔除。时间包含 event 区间内的执行和提交间隙，排除分配、传输、CPU 参考与回读。
- NCU 主诊断：1024³，每版 3 次，application replay、clock-control=none、cache-control=none，预热 30 次；另有清缓存 kernel replay、base 频率策略和缓存指标补采。它们是不同测量条件，不能与普通计时直接相减。预热和“不清缓存”也不保证每次缓存状态完全一致。

| --- | --- | --- | --- | --- | --- |
| 128×128×128 | 11.58 ± 1.86 | 11.36 ± 1.29 | 12.55 ± 2.08 | 1.019× | 0.922× |
| 512×512×512 | 287.06 ± 29.14 | 214.64 ± 24.71 | 130.54 ± 15.24 | 1.337× | 2.199× |

1024³：shared 相对 naive 加速 1.348×，register 相对 shared 再加速 1.717×，相对 naive 为 2.314×。逐次 GFLOP/s 的均值为 998.16 / 1338.19 / 2300.44；吞吐分子使用 2MNK，逐次吞吐均值不等于 2MNK 除以平均时间。

按 run 配对，naive−shared 的时间差为 563.42 μs，95% t 区间 [341.46, 785.39]；shared−register 为 676.51 μs，区间 [527.37, 825.65]。本批中大尺寸的排序有支持。128³ 的三种两两差值区间均跨零，例如 shared−register 为 [-2.84, 0.45] μs，不能给出稳定排序，也不能据此证明三者等效。

## 2. 沿着“代码变化→工作计数→资源压力→时间”分析

### ① naive→shared：主要减少请求压力，不能等同于减少 16 倍 DRAM 流量

下面是主诊断 3 次均值；各项单位和未平均值见后文。

| 1024³ | naive | shared | register |
| --- | --- | --- | --- |
| global load request | 67,108,864 | 4,194,304 | 2,097,152 |
| global load sector | 134,217,728 | 16,777,216 | 8,388,608 |
| shared load warp 指令 | 0 | 41,943,040 | 20,971,520 |
| shared store warp 指令 | 0 | 4,194,304 | 2,097,152 |
| 总 warp 指令（百万） | 173.769 | 117.146 | 117.375 |
| 有效线程 FFMA | 1,073,741,824 | 1,073,741,824 | 1,073,741,824 |
| L1 sector hit rate % | 87.45 | 6.82 | 2.28 |
| L2 TEX read sector（百万） | 16.700 | 15.576 | 8.400 |

**首先验证改动确实发生。** global load request 从 67,108,864 降为 4,194,304，恰为 1/16；按每个 C 元素归一化是 64→4 个 warp request。三版有效线程 FFMA 都是 1024³=1,073,741,824，没有靠少做数学工作取巧。global store 也均为 32,768 request、131,072 sector，符合每个 C 写一次的 4 MiB 输出。

**再检查流量经过哪一级。** global load sector 只减少 8 倍，而不是 16 倍：naive 为 2 sector/request，shared/register 为 4。naive 同一 warp 中 A 有重复地址，B 的两组半 warp 读取同一段；“2 比 4 小”不能单独证明它的合并访存更好。完整有效 tile 下，协作加载让每条加载服务更多独立值。这里的 sector 是 L1/TEX 入口流量，尚未扣除 L1 命中，不是 DRAM 流量。

1024³ 的 A/B 各 4 MiB、C 为 4 MiB，逻辑工作集共 12 MiB，小于 32 MiB L2；容量上可以容纳，不等于已经证明实际驻留。naive 的 L1 sector hit rate 约 87.45%，shared 约 6.82%；这是聚合 sector 比率，不是 A/B 各自或逐条 load 的命中率。显式 shared 复用替代了大量重复 global 查询，命中率下降本身不是退步。与此同时，L2 TEX read sector 仅由约 16.70M 降为 15.58M，远没有 16 倍变化；这是“大量重复请求已在 L1 层被吸收”的支持证据。L2 精确命中率存在采集异常，不能再从该比率反推命中/未命中的字节数。

**因此不能由 16 倍请求削减预测 16 倍加速。** 实际收益约 1.35 倍；片上 global 请求确实大幅减少，但原有缓存已吸收复用，shared 版又引入 shared 读写和同步。现有数据不能将这些因素各分摊成多少微秒。以下指标更支持请求入口及通信相关压力，而非 DRAM 带宽饱和：

| 主诊断 3 次均值 | naive | shared | register |
| --- | --- | --- | --- |
| NCU 单次 kernel μs | 1,900.28 | 1,460.11 | 840.32 |
| SM 时钟 GHz | 2.781 | 2.756 | 2.747 |
| LSU 入口请求 % peak | 97.82 | 96.42 | 84.05 |
| L1 shared/global data wavefront 管线 % peak | 73.41 | 61.29 | 51.26 |
| DRAM throughput % peak | 1.33 | 1.24 | 0.88 |
| Issue active % elapsed | 31.62 | 27.99 | 48.90 |
| Eligible warps / scheduler active cycle | 1.85 | 1.50 | 2.35 |

L1/TEX throughput 和 SM throughput 在此都跟随 LSU 入口项，约 98%/96%/84%；不能把“SM throughput 98%”读成 FP32 算力打满。data wavefront 管线仅约 73%/61%/51%，FMA/FMAheavy/FMAlite 三类管线也没有给出算术管线饱和证据。主诊断 DRAM 吞吐约 0.9%～1.3%，清缓存组也仅约 1.9%～3.4%；当前没有将主瓶颈归为 DRAM 带宽的依据。聚合 throughput 是子项的高值，应继续看具体子管线。[NCU 吞吐与内存表口径](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#metrics-structure)

### ② shared→register：复用有效，但总指令几乎不降

global request/sector、shared load/store warp 指令均恰好再减半。要拆开来源：BM/BN 从 16 增到 32 使同一输出区域所需 global 加载减少；每线程四个输出的外积复用减少了 shared 读取。这两个因素本版同时改变，不能将全部加速归为纯寄存器复用。

shared load 的实际 warp 指令为 41,943,040→20,971,520。它不是源码标量读取次数：SASS 中两版都混有 LDS 和 LDS.128，编译器把部分相邻 K 项合成了宽加载。源码模型适合预测方向，最终计数要以编译结果验证。

**总 warp 指令却为 117.146M→117.375M，近乎持平。** register 版相对 shared 的收益不能解释成“总指令更少”。观察到的是指令组成与等待状态改变：入口请求压力降低，issue 从 27.99% 升至 48.90%，eligible 从 1.50 升至 2.35。不能仅凭现有总量解释哪些整数/控制指令抵消了减少的访存指令；若要细分，需要动态整数、uniform、控制指令及逐 PC 计数。

将累积 stall warp-cycle 除以累积 active warp-cycle，得到另一种有明确分母的比较：

| 累积 warp-cycle 状态占比 | shared | register |
| --- | --- | --- |
| mio_throttle | 50.88% | 33.52% |
| barrier | 14.34% | 7.27% |
| long_scoreboard | 14.86% | 24.99% |
| short_scoreboard | 2.45% | 3.43% |

MIO throttle、barrier 的占比与绝对计数均降低，结合 shared 读写减半，支持“通信/发射压力得到缓解”。但它们不是可相加的关键路径时间：没有逐 PC 关联，不能说各自贡献了多少微秒，也不能证明四条独立累加链各贡献多少加速。long/short scoreboard 的占比反而上升，而 kernel 更快，说明优化后剩余等待的构成会改变；高 stall 百分比本身不是回退证据。

要隔离纯线程内复用的收益，后续需要保持 BM/BN/BK、线程数、输出归属与边界处理相同，只改变加载/复用策略的控制版本，并确认编译器没有将对照优化成相同 SASS。本轮没有改写你的算法来制造这个控制组。

### ③ 先排除低价值方向，再决定下一步

- **Occupancy / 寄存器容量**：39/38/40 registers per thread；三版 register limit 与 warp limit 均为 6 block/SM，理论上可达 100%。实际 occupancy 为 97.53%/98.47%/94.50%，register 更快却略低。local load/store 指令三版均为 0，SASS resource 的 LOCAL/STACK 也为 0；没有当前输入下由寄存器溢出拖慢的证据，先不为压寄存器而改代码。
- **Shared 容量**：launcher 请求是 0/2/4 KiB，NCU 实际 allocated 为 1/3/5 KiB。报告元数据进一步给出三版 driver shared 均为 1 KiB、static shared 均为 0；因此 cuobjdump 的 SHARED:1024 不能直接当作用户声明的静态数组。不能忽略驱动额外部分或把 naive 记成实际分配 0。shared 驻留上限为 16/21/12 block，均不比最紧的 6 block 更小，容量不是本次主要约束。
- **Bank conflict**：主诊断 shared/register 读冲突约 5,295/541，对应读 wavefront 约 50.337M/25.166M；比值约 0.0105%/0.0021%，写冲突为 0。没有严重冲突证据，暂不套用转置的加一列 padding。wavefront/指令约为 1.2 也不等价于 20% bank conflict；存在 LDS.128，要精确解释额外 wavefront，需要逐 PC 的 ideal/actual wavefront。
- **小尺寸与尾部**：128³ 时 register 仅 16 block，少于 26 SM，可提出并行度不足的假设；但本批不能区分它与提交间隙/调度开销，需同环境 Nsight Systems 时间线及更细的尺寸扫描。矩形尾部组仍受益，但没有只改变边界因素的控制，不能把它相对 1024³ 的差异全归给尾部。该尾部组 shared/register 的填充计算开销可由 tile 几何推导约 2.5%，不等于同等时间损失。

## 3. 采集异常与本轮不能下的结论

1. **精确的预热 L2 命中率不可用。** 初次 kernel replay/no-flush 出现 >100%；改 application replay 后仍有 102.05%、100.73%。最小集补采 read sector 与 read-hit sector，仍有分子大于分母；导出的报告元数据证明该最小集也需要 3 次回放，并没有取得同一遍的分子分母。因此不能把这组数据称为同遍命中率，也不能修剪到 100%、取平均“修好”，或据此解释缓存退化。需进一步获得稳定且可比的回放状态、隔离其它 GPU 活动，并核查可同遍采集的 counter 口径。异常根因本轮未确定；不把它归罪于 kernel。[NCU：越界指标与多遍采集](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#faq)
2. **base 策略不等于严格同频控制。** base 组平均 SM 时钟分别为 1.244/1.097/1.437 GHz，naive/shared 样本也明显波动，所以仅保留作运行条件敏感性记录，不用它划分核心效率贡献。主 application 组时钟约 2.781/2.756/2.747 GHz，更接近，但也不是外部固定频率实验。
3. **冷/预热差值不能当作缓存收益。** 冷组 kernel μs 为 1930.99/1636.85/850.05，主 application 组为 1900.28/1460.11/840.32；replay 与时钟也改变，不能把两组时间相减当“清缓存开销”。[NCU Replay 与 Cache Control](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#cache-control)
4. **不拿 DRAM 原始写字节倒推 C 写了几次。** 硬件写回不必与该 kernel 的 C payload 一一对应，且没有隔离桌面其他 GPU 客户端。检查输出覆盖优先看稳定的 global store request/sector 与完整数值校验；原始 DRAM read/write 全部保留。

## 4. 迁移到其他 kernel 的分析顺序

1. **固定目标与计时边界**：用户实际关心的时间、输入尺寸、校验、预热、重复次数、顺序；先看波动，不能先挑最快样本。
2. **写出改动预测与不变量**：本例是 global 请求 1/16、再 1/2；FFMA 与输出写入量不变。明确计数单位是 thread/warp、scalar/sector，以及处在哪一级存储。
3. **验证编译后的工作量**：用稳定的 counts 和 SASS 核对；按同一输出量/FLOP 归一化。源码读取次数、机器指令、L1 sector、L2 流量、DRAM 字节不是同一件事。
4. **定位最紧资源与未隐藏的等待**：展开聚合 throughput，联合 issue/eligible、资源驻留与 stall；不能以单个高百分比定瓶颈，也不能把 warp-cycle 占比直接变成可消除时间。
5. **做条件控制并守住证据边界**：确认 clocks/cache/replay 真的可比；反常指标先审计采集，再谈算法。需要因果贡献时做单因素控制；数据不够就明确缺少的观测。

若继续优化，本批更值得优先检查 shared/MIO 相关指令的逐 PC 等待和调度，以及保持配置不变的复用对照；当前不优先做 bank padding、追求更高 occupancy 或宣称已达到 FP32 峰值。
