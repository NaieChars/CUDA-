1 · 先知道自己正在读哪一层

程序、机器码、汇编、反汇编

你写的 sum += a * b; 表达要算什么；GPU 最终接收的是按其指令格式编码的机器码。汇编用可读的名称、寄存器和操作数描述这些低层操作。把机器码转换为可读指令文本的过程叫反汇编。我们先练阅读，不需要先会手写汇编。

把它理解成“检查编译器最终安排了哪些操作”很合适。反汇编通常不能还原原来的变量名、循环写法和注释；编译器可能展开循环、合并加载、重用寄存器、调整指令顺序。

你写的 CUDA C++（kernels.cu）
           ↓ 编译前端
PTX：面向虚拟指令集的中间表示；寄存器也是虚拟的
           ↓ ptxas / 后续机器码生成
目标 GPU 的机器码，存放于 cubin 等设备代码对象中
           ↓ cuobjdump / nvdisasm 反汇编
SASS：目标 GPU 机器指令的可读文本

另一条可能路径：程序携带 PTX → 驱动 JIT → 当前设备的机器码

sgemm.exe 同时含主机程序和设备代码；cubin 是设备代码对象，不等于整个 exe。PTX 有助于理解语义，但一条 PTX 不保证对应一条 SASS；PTX 的虚拟寄存器数也不等于硬件寄存器用量。本课的计数对象是实际 sm_120 编译结果。一手依据：PTX ISA Introduction。

sm_120 指目标 GPU 架构，不是“120 个 SM”。/*03c0*/ 是函数内指令偏移，不是源码第 3c0 行，也不是耗时。右侧的 0x... 是机器编码；今天不需要按位解码。

第一轮口头检查：SASS 和 PTX 各回答什么？

PTX 帮你看中间层的操作语义；实际 SASS 帮你检查某个目标版本最终生成的指令。两者都不是逐周期执行录像，也不能仅凭文本知道哪条指令花了多少时间。

3 · 一行指令到底怎么读？

先读“操作名 → 写哪里 → 从哪里取值 → 是否有条件”。对下面 LDS / FFMA，目的操作数在前；不要把这个位置规则机械套到 store 上。

/*03b0*/ LDS     R28, [R27+0x400];
/*03c0*/ LDS.128 R8,  [R0];
/*0420*/ FFMA    R8,  R8, R28, R29;
/*0600*/ @!P0 BRA 0x2a0;

这些来自你的 shared kernel；为了阅读，省去了编码和调度注记，指令语义操作数保持原样。完整行中的 &wr、&req、?trans、?WAIT 先跳过；它们不是 profiler 实测的纳秒数。

写法本课读法一个常见误会
R8、R28线程的通用寄存器操作数R8 不是整个 warp 共享的一个变量
[R27+0x400]访问地址 R27+1024 处的内存方括号表示取内存，不是普通相加
0x10 / 0x40 / 0x40016 / 64 / 1024；此处地址偏移按字节+0x10 不是跨 16 个 float
P0、@P0、@!P0谓词；条件真 / 条件假时执行谓词不是指针，也不是线程编号
LDS / STSshared → 寄存器 / 寄存器 → sharedSTS 的第一个操作数是写入地址
LDG / STGglobal 加载 / 存储指令族指令数不等于 DRAM 事务数
FFMA D,A,B,CD ← A×B+C，FP32 融合乘加不是三个操作数的连乘
BRA / BAR.SYNC…控制流跳转 / block 同步屏障BRA 与 BAR 不是同一种操作
MOV / IADD / ISETP搬值 / 整数加 / 比较并设置谓词不是每条指令都在做浮点数学

指令族可查 官方指令参考；具体片段和架构以本机导出为准。RZ 表示零寄存器，UR 是 uniform 寄存器命名；初次遇见先认出类别，不在本课展开其分配规则。

3.1 · LDS.128 的 128 是什么？

这里 LDS R28,[...] 对每个参与线程取一个 32 bit 的值；LDS.128 R8,[R0] 对每个参与线程取 128 bit，即 16 字节，在这个 FP32 例子中是四个相邻 float，写入 R8,R9,R10,R11。它仍是一条 SASS 指令。128 不是“128 个线程”或“128 条指令”。

在满 warp、32 个 lane 都参与时，一次 LDS.128 对应 32×16=512 字节的逐 lane 逻辑读取量之和；不同 lane 可以读重复地址，不能因此说有 512 字节不同的数据，更不能说一次就发生一个 512 字节物理事务。

练习 2：地址从 0x400 到 0x440，跨多少字节、多少个 float？

3.2 · 谓词和循环

@!P0 BRA 0x2a0 表示相应 lane 的 P0 为假时参与该跳转，目标是当前函数内 0x2a0。反汇编中的 0x600 跳回更小偏移，是循环回边的线索。还需要追查 P0 由哪个比较设置，才能说它代表什么条件。

本函数在 /*0340*/ 将 K 段位置加 0x10，在 /*0360*/ 比较是否到达 K，随后在 /*0600*/ 判断是否回到下一段。这些线索与源码 k0 += 16 对应。别见到 P0 就想当然地把它解释成某个源码 if；同一个谓词寄存器也会被复用。

4 · 读指令片段：数据从哪来，又被谁使用？

4.1 · 为什么 A 可以宽加载，B 仍多为标量加载？

// shared 版的内层数学循环
for (int e = 0; e < 16; ++e)
    sum += as[16 * ty + e] * bs[16 * e + tx];

固定一个线程，沿 e 观察：A 相邻项只差 1 个 float（4 字节），B 相邻项差 16 个 float（64 字节）。这是同一线程跨 e 的地址关系；与同一时刻多个 lane 的合并访存问题要分开。这里的编译结果将 A 的四个连续 e 项合成 LDS.128，而 B 仍逐项 LDS。

本二进制中，A 地址由 R0 形成，B 地址由 R27 加偏移形成；前面的地址构造和源码布局、16 字节与 64 字节的步长共同支持这个对应。单凭一个寄存器名字无法判断 A/B。

/*03a0*/ BAR.SYNC.DEFER_BLOCKING 0x0;
/*03b0*/ LDS     R28, [R27+0x400];  // B 的当前 e
/*03c0*/ LDS.128 R8,  [R0];         // A 的四个连续 e → R8..R11
/*03d0*/ LDS     R32, [R27+0x440];  // B 的下一 e
// 若干其他加载省略
/*0420*/ FFMA R8, R8, R28, R29;
// 一条其他加载省略
/*0440*/ FFMA R9, R9, R32, R8;
...
/*05f0*/ BAR.SYNC.DEFER_BLOCKING 0x0;
/*0600*/ @!P0 BRA 0x2a0;

两道 BAR 对应当前程序的 block 同步结构。优化后指令可能跨源码行交错，屏障的完整后缀也涉及架构语义；本课只要求识别同步位置，不把它简化成“屏障前所有算术都已全部结束”。

4.2 · R8 不是永远等于变量 a

在 0x3c0 后，R8 装着一个 A 元素；0x420 的 FFMA 先读取旧 R8，再把部分和写回 R8。下一条 FFMA 用新 R8 当加数。寄存器名字是可复用的存储位置，不是固定源码变量名。

5 · 主实验：32 次标量读取，为何只有 20 条 load？

5.1 · 先固定所有计数单位

本段只研究 shared 版，M=N=K=1024，block=16×16，BK=16。所有 tile 都完整，没有尾部裁剪。先区分下面四个量：

量你在数什么本段例子
源码标量读取一个线程读到多少个 float 操作数每 K 段 A/B 各 16 个
静态指令反汇编里一个位置的一条指令K 段体中 20 条 shared load
动态 warp 指令每个 warp 运行该指令的次数20×段数×warp 数×block 数
pred-on 线程指令谓词为真的参与线程操作数满 warp 的 FFMA 每次有 32 个

profiler 显示 inst 时仍要读完整指标名，warp 与 thread 的分母不同。本课使用的 shared load 指标是 smsp__sass_inst_executed_op_shared_ld.sum；FFMA 用 smsp__sass_thread_inst_executed_op_ffma_pred_on.sum。前者不能再随手乘 32 后仍称为同一个指标。指标结构与采样区别参见 Profiling Guide。

5.2 · 源码模型与机器模型各算一次

源码：每线程每段读 A 16 次、B 16 次，共 32 个 float 操作数。实际 K 段体：A 用 4 条 LDS.128，每条取 4 个 float；B 用 16 条 LDS，各取 1 个。

同一线程、一个 K 段：
读到的 float 操作数 = 4×4 + 16×1 = 32
执行的 shared load 指令 = 4 + 16 = 20

加载宽度改变了指令条数，保留了这些逻辑操作数。
32 不能直接拿来替代 shared-load warp 指标中的每段指令数。

在 原始导出 中，shared 函数含 16 条 LDS、4 条 LDS.128、16 条 FFMA、2 条 BAR。内层 e 循环已经展开成这一段，外层 K 分块仍通过回边重复。搜到 20 行指令只能得到静态数；下一步才把执行次数乘进去。

练习 4：每线程每段多少条 shared load，多少个 float 操作数？

5.3 · 从一个 warp 推到整个 grid

一个 block 有 256 个线程，即 8 个完整 warp；grid 为 64×64=4096 个 block；K=1024，一共 64 段。这个 kernel 的计算区没有 predicated LDS，且所有线程参与每段计算，故此例可按统一循环次数相乘。

练习 5：先自己填四个中间量，再与报告核对。

推导完成后再看：两个交叉核对 
shared load warp 指令 = 4096×8×64×20 = 41,943,040
FFMA warp 指令        = 4096×8×64×16 = 33,554,432
FFMA pred-on 线程指令 = 33,554,432×32 = 1,073,741,824
数学模型              = M×N×K = 1024³ = 1,073,741,824
常用 GEMM FLOP 口径    = 2×M×N×K；一条 FFMA 计两次浮点操作

如果误把 32 个源码读取当成 32 条 LDS，便会预测 67,108,864 条 warp load，与报告不符。这个偏差首先要求检查编译结果和单位，不是立即怀疑测量故障。

特别检查：旧采集只指定了一组总量指标，没有专门请求逐 PC 的 SourceCounters / warp sampling。Source 页能显示 SASS，不代表同时拥有每条指令的 stall 样本；缺列、空白、N/A 都不能当作零等待。这节不为“把表填满”临时重采。

7 · 扩展半步：指令证据怎样进入性能判断？

7.1 · 三个问题分别需要什么证据

问题需要的证据本节能到哪一步
是否减少预期工作？源码模型 + SASS + 动态计数本节主练习，能够核对
整体是否更快？相同口径的多次普通计时读已有结果，练解释不确定性
为什么影响时间？依赖、资源、定向观测或控制实验识别缺口，提出可区分的假设

“20 条 load 比 32 个标量读取少”证明了编译层面的合并，不能直接预测时间按 20/32 缩短。宽指令、实际处理的 lane 地址、流水线能力、同步和依赖共同影响执行；bank wavefront、全局请求、DRAM 流量也是不同层级。一个 32 bit shared load 可以因地址模式产生不同处理量，一个宽 load 也不能直接等同一次物理事务。

7.2 · 从已有性能报告练一次有边界的解释

已有报告记录 shared → register 的 shared load 从 41,943,040 降至 20,971,520，普通 1024³ 均值从约 1.620 ms 降至 0.944 ms。可以说整体时间改善、相关通信工作减少有支持；第三版同时改变输出 tile 和线程内复用，不能把全部收益划归某个因素。

课堂先自己回答：“下一步观测什么，才能更接近原因？”可考虑检查哪些 shared 指令变了、每输出对应多少动态指令、是否有独立累加链；这些都有明确对象。不要从完整指标表中随机挑一个百分比来解释。

7.3 · 热点与等待：加量部分的概念预告

PC 是指令位置。warp sampling 会在若干时刻观察 warp 的调度状态，并关联指令位置；它不是给每条指令装一个秒表。将来即便看到一个 FFMA 附近有依赖等待样本，也应回查它消费的加载值或之前的累加结果，不能直接下结论“FFMA 算得慢”。一手阅读：Profiling Guide，Warp Sampling。

本节只识别这个边界，不要求熟悉全部 stall 原因。如果以后真的做逐 PC 诊断，先查看本机支持和旧报告可用项，再决定小规模补采，而不是先承诺旧报告里一定有数据。

7.4 · 用一个已有区间理解小收益

128³ 的普通计时中，shared−register 的 95% 配对差值区间为 [-2.84,0.45] μs，跨过零。它支持“这批数据不足以稳定判断两者排序”，不证明“完全没效果”或“二者等效”。该区间以 10 轮近似独立差值为前提；同一进程内重复 300 次得到的平均值，不变成 300 个独立实验样本。

未来做新微调时，先 A/A 看测量本身的波动，再考虑交错 A/B 或 AB/BA 形成配对差值。A/A 中 A 是同一版本重复测；A/B 中只改变一个目标因素。先写预测、独立轮次和停止条件，避免看到一点差异就不断挑最快样本。

讨论题反馈：区间跨零，下一步一定要继续测吗？

不一定。先看这个小收益是否值得追、当前不确定性是否会改变决定、能否先选一个更大且可预测的工作量变化。若确需补测，事先约定批次数或精度目标；若仍不确定，就记录“待验证”。不要把无限加样本当作唯一进展。

7.5 · 三档结论写作

已确认：本版本 shared 的每个 K 段有 4 条 LDS.128、16 条 LDS；
        1024³ 的动态 shared-load warp 计数与 41,943,040 吻合。
有支持：已有报告显示 register 版相关通信工作减少、整体更快。
待验证：纯线程内复用贡献多少时间；哪个 PC 的等待处于关键路径。

“已确认”始终带着版本、输入和计数口径。下一项好观测，应能区分至少两个解释，而不只是再多一个数字。

8 · 收课：你独立完成一次迁移

主练习：保持本二进制与 shared 配置不变，把 M=N=K 改成 512，只做纸面预测。给出 grid、每 block 的 warp 数、K 段数、shared-load warp 计数、pred-on 线程 FFMA 计数。这里没有声称已经对 512³ 重新采集这些指标。

思考题：若尺寸是 1023×1009×1031，还能直接用 MNK 当作执行的线程 FFMA 吗？先解释，再展开。

尾部题反馈

不能。这版通过补零保持全部线程执行完整 K tile，最后才裁剪写出；多出来的输出线程及 K 尾部仍做乘加。在保持这份 SASS 的前提下，shared-load 预测为 ceil(M/16)×ceil(N/16)×8×ceil(K/16)×20；这里是 64×64×8×65×20=42,598,400。pred-on 线程 FFMA 对应填充后的 1024×1024×1040=1,090,519,040，逻辑问题的常用 FLOP 分子仍可定义为 2MNK。不要把逻辑有效工作、实际执行工作和最后合法输出混成一个数。本题是模型推导，未补采运行。

完成标准与两次回忆

  1. 关掉答案，口头解释源码、PTX、SASS、cubin 的关系。
  2. 自己找出 shared 函数，读懂一条 LDS.128、一条 FFMA 和一条带谓词的 BRA。
  3. 画出 LDS → FFMA → FFMA 的依赖，说明寄存器为何会改存别的值。
  4. 从 20 条静态 load 推出 41,943,040 条动态 warp load，再用旧报告核对。
  5. 写出一个已确认结论和一个待验证问题，不把指令变化直接换算成加速。
