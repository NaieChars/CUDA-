先回忆一个依赖

基础版中，加载到 shared memory 后为什么要同步？先用一句话回答，再展开。

核对解释

后续线程要读取其他线程写入的 s 槽位，必须先保证加载完成并可见。同步依据。

把 B × I 个输入，先压成 B 个局部和

记 B = blockDim.x，I = items_per_thread。基础版每个 block 处理 B 个数；本版处理 B × I 个数。每个线程用一个私有 float sum 累加 I 个输入，再执行 s[tid] = sum。后半段仍是原来的 B 元素求和树。

全局输入 B × I 个数
        ↓ 每个线程独立累加 I 个数
      B 个线程局部和
        ↓ 写入 shared memory，再同步
      原来的 block 内求和树
        ↓
      1 个 block 部分和

这个组合对应 NVIDIA 教程中的 Algorithm Cascading（幻灯片 31）。局部 sum 通常可由编译器放在寄存器中，实际分配由编译结果决定。

让同一轮的相邻线程读取相邻地址

block b 的起点是 base = size_t(b) * B * I。线程 tid 第 j 次读取：

idx = base + tid + size_t(j) * B

用 B=4、I=3、base=0 看分工（4 个线程仅用于示意，项目实际 B 至少为 32）：

循环轮次线程 0线程 1线程 2线程 3
j = 0in[0]in[1]in[2]in[3]
j = 1in[4]in[5]in[6]in[7]
j = 2in[8]in[9]in[10]in[11]

横着看：同一轮不同线程的地址连续。竖着看：单个线程的多次读取相隔 B。判断合并访存，要看同一 warp 执行同一条加载指令时的地址，参见 NVIDIA Best Practices §10.2.1。

    if (idx < n)

加载循环中无需屏障：线程只更新自己的 sum。循环结束后，每个线程无论是否读到有效数据，都写入一个已初始化的局部和并执行屏障。尾部逐次检查 idx，不能因本轮越界就遗漏后续的 shared memory 写入与同步。

先预测，再验证

对于 n=16,777,216、B=256，第一轮 I=1 产生 65,536 个部分和；I=4 产生 16,384 个。每个 block 的求和树仍有 8 层，原始输入仍全部读取一次。变化来自更少的 block 内归约与中间部分和，而不是少读了四分之三的原始数组。这是由本项目分工推导的预测，不是性能测量结果。

I=4 的完整计划为 16,777,216 → 16,384 → 16 → 1，仍然是 3 轮 kernel。更少的部分和不保证更少的 kernel 启动。

I 增大也会拉长每个线程的串行工作，并减少可调度的 block。速度是否提升、提升多少，要实际测量。

cmake --build build --config Release --target reduction --parallel

# 先检查 block 容量左右的尾部，I=3 也要覆盖。
.\labs\reduction\scripts\run_benchmark.ps1 -Modes 1 -Sizes 1,31,32,33,255,256,257,767,768,769,1003,1023,1024,1025 -Blocks 256 -ItemsPerThread 1,3,4 -CheckOnly -Repeat 1

# 再控制 block 和 n，只扫描每线程元素数。
.\labs\reduction\scripts\run_benchmark.ps1 -Modes 1 -ItemsPerThread 1,2,4,8 -Repeat 3

计时脚本测完整归约；ncu 脚本测首轮，两者不要直接混作同一个时间。改变累加分组可能改变浮点误差，校验使用框架已有容差，参见 浮点加法的非结合性。
